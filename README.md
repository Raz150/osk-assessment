# Gameweek Club: Second-Half League

A single responsive landing page for **Gameweek Club**, a fictional community fantasy football mini-league for the **Malaysia Super League**, based in the fictional town of Bukit Cempaka, Selangor. Entry donations go to a fictional youth football club, Cempaka Muda FC.

> Not affiliated with the Malaysian Football League (MFL), the Malaysia Super League, any club or any official fantasy game. All names, dates, figures and organisations are fictional demo content.

## Audience and primary action

- **Audience:** casual or lapsed Malaysia Super League fans in Bukit Cempaka and nearby areas. Some missed the start of the season, some saw their team fall apart, and some find fantasy football intimidating.
- **Primary action:** **register interest** in the Second-Half League (*Liga Pusingan Kedua*), which starts with the second round of the season.
- **Visitor flow:** read the hero, then compare formats (tabs), then press "Choose [format]". That fills in the format on the form, and the visitor registers.

## Setup, run, test

Requires Node 20+.

```bash
git clone https://github.com/Raz150/osk-assessment.git
cd osk-assessment
npm install                      # Tailwind CLI (dev only)
npm run build                    # css/input.css → css/styles.css (minified)
python3 -m http.server 8080      # or: npm start (runs serve@14.2.4 through npx)
# open http://localhost:8080
npm run dev                      # optional, in a second terminal: rebuild CSS on every save
npm test                         # unit tests for the form validation rules
```

`css/styles.css` is **generated** but committed, so GitHub Pages can serve it without a build step. Always run `npm run build` before committing a change to the HTML or `css/input.css`.

A local server is needed rather than opening the file directly, because `js/main.js` is an ES module and browsers block modules loaded from `file://`.

## Stack choice

**Static HTML, Tailwind CSS (v4, through its CLI) and plain JavaScript.**

- **No JavaScript framework.** The site is one page with three small interactions, and React or Next.js would add bundle size and complexity without adding anything the page needs.
- **Tailwind for styling.** Brand tokens live in one `@theme` block, so colours, fonts and the radius are defined once and every utility (`bg-primary`, `shadow-hard`, `rounded-brand`) uses them. Repeated patterns (buttons, cards, tabs, form fields, FAQ items) are component classes in `css/input.css` built with `@apply`, so they stay consistent. One-off layout is done with utilities in the HTML.
- **The CLI, not the CDN script.** Tailwind's CDN "play" script compiles in the browser and warns in the console that it isn't for production. The CLI outputs one minified file (about 31 KB, 6 KB gzipped) that contains only the classes the page uses.
- **The validation rules** are in their own ES module, so they can be unit-tested with Node's built-in test runner without extra dependencies.

## Design rationale

### Brand rules

| Rule | Applied as |
|---|---|
| **Black outlines and hard shadows.** Every surface has a 3px ink-black border, and raised items (cards, buttons, form, photo) cast an unblurred black offset shadow. This is the neobrutalist signature: flat, bold, nothing hidden. | `box` utility, `--shadow-hard-*` tokens in `css/input.css` `@theme` |
| **Hot pink `#ff7ce0` means "act here or selected".** It's used for the primary button (hover `#ff30cd`), the selected tab, the open FAQ item, the key deadline, the headline and the charity band. Soft pink `#ffd3f4` is the page background. | `--color-primary`, `--color-primary-hover`, `--color-accent`; `.btn-primary` is the only pink button |
| **Text is always black on pink.** Black on all three pinks passes WCAG AA (8.3:1, 5.9:1, 14.3:1). White text is never placed on pink (only 3.2:1 on the hover pink). | `--color-ink` `#111111` |
| **Two typefaces.** Archivo Black (uppercase) for headings, chunky like a match-day poster. Inter for body text, for readability. | `--font-display` and `--font-sans` |
| **Tailwind's spacing scale in 8px steps (mostly), one 10px corner radius, slight rotations only on stickers and highlights.** | `--radius-brand`, `.sticker` |

### Key decisions

1. **Original branding that steers clear of the real game.** The audience will know the official fantasy game and Malaysian club colours, so the site uses a deliberately unexpected neobrutalist pink theme instead: no MFL or club colours, crests, photos of real professional players or league logos. A disclaimer appears in both the FAQ and the footer. This avoids misleading visitors and avoids using assets I don't have permission for.
2. **Neobrutalism for a friendly, low-pressure league.** Football sites usually look serious and corporate. Thick outlines, sticker-like labels and buttons that visibly press in make the page feel playful and approachable, which suits people who find fantasy football intimidating. The hard edges also keep interactive things obvious: every button has the same border-and-shadow "lift", and pink always marks the next step.
3. **Formats as tabs that fill in the form.** The biggest worry for this audience is "which league is for me?". Tabs keep the three formats the same shape (suits, time, entry, prize), so they're easy to compare without a long page, and the "Choose" button carries that decision into the form so the visitor doesn't have to make it twice.
4. **Local voice.** The copy is in English, the common language of Malaysian football fans online, with familiar Malay terms such as *Pusingan Kedua*, *padang*, *makan* and *Jom!*. Prices are in RM and the deadline is in MYT. This makes it read as a real neighbourhood league rather than a generic template. I used "second round" instead of a gameweek number so the content doesn't depend on the exact MSL fixture count.
5. **Hero message aimed at latecomers.** The site launches mid-season, so the headline speaks directly to people who think they've missed out: "Missed the start? Join the second half." The photo of a player mid-volley adds energy, and a "Pusingan 2" sticker on it repeats the "second round" message.

### Plan vs finished site

The finished page follows the wireframe's content order and flow. Differences:

- **Hero visual:** the wireframe planned an SVG pitch illustration beside the text. The build uses a dark three-column hero: decorative shapes, then the copy, then a black-and-white photo of a player striking a volley, in a thick soft-pink frame. A real photo makes the league feel real, and black and white keeps the green grass from clashing with the pink palette. I tried two other photos first (players lined up on a futsal halfway line, then an aerial view of a centre circle) before choosing this one for its movement. Below 1024px the columns stack, the decoration column is hidden, and the menu collapses, because the logo block and full nav don't fit side by side at tablet width.
- **Visual theme:** the first build used a pitch-green and yellow palette. I re-themed it to neobrutalism in pink (see Brand rules) to make the page more distinctive and playful. Because all colours, fonts, shadows and radii are tokens and repeated patterns are component classes, the re-theme mostly changed `css/input.css` and the class names in `index.html`; the content and JavaScript didn't need to change.
- **Charity section:** the wireframe has a paragraph and three equal tiles. The build splits it into two columns: the total raised as a large sticker on the left, and the three outcomes as stacked cards on the right. The tiles were the same pink as the band behind them and looked flat, and the right half of the section was empty.
- **Key dates at tablet width:** the wireframe goes straight from vertical (mobile) to a row of four (desktop). The build adds a 2×2 grid between 640px and 1024px, because four columns were too cramped at those widths.
- **FAQ width:** narrowed to a 48rem reading column on desktop instead of the full container, for a comfortable line length.
- **Form status message:** added an error summary at the top of the form ("Please fix N problems below") as well as the inline errors in the wireframe.

## Interactions

| Interaction | Purpose | States shown | Keyboard |
|---|---|---|---|
| **Format tabs** with a "Choose [format]" button | Compare the three formats, then take that choice into the form (the main task) | Selected tab turns hot pink and "presses in" (shadow removed) (`aria-selected`) | Tab moves into the tab list; ←/→ wrap round; Home/End; Tab moves into the panel |
| **Validated demo registration form** | The primary action | Inline error per field (`aria-invalid` plus a message linked with `aria-describedby`), an error summary, a success message; errors clear while the visitor fixes them | Native controls; focus moves to the first invalid field, or to the success message |
| **FAQ** (native `<details>`) | Answers the questions that stop people joining | Open item's question turns hot pink with a divider | Native |
| **Mobile menu** | Navigation below 1024px | `aria-expanded`; button text "Menu" / "Close" | Escape closes it and returns focus to the button |

**Demo form:** `submit` is always cancelled with `preventDefault()`. Values are never sent, stored (no cookies or storage) or logged. The success message repeats the team name on the page only, and then the form is reset. The page says this next to the form.

**Without JavaScript:** all three format panels stay visible and the menu stays expanded, so the content and navigation are still usable.

## Deployment

Hosted on **GitHub Pages** from the `main` branch, root folder, over HTTPS.

1. Push to `main`.
2. In the repo, go to **Settings → Pages → Build and deployment**, choose *Deploy from a branch*, `main`, `/ (root)`. Only needed once.
3. GitHub publishes to `https://raz150.github.io/osk-assessment/` within about a minute. The progress is under the **Actions** tab ("pages build and deployment").

All asset paths are relative (`css/styles.css`, not `/css/styles.css`), so the site works under the `/osk-assessment/` sub-path.

### Verification and a resolved issue

- **Resolved: form status lost its styling after the Tailwind move.** `showStatus()` set `status.className = ...`, which replaced every Tailwind class on the element. I changed it to set `data-state="error|success"`, styled with `data-[state=…]:` variants, and checked both states visually and with the automated run.
- **Resolved: horizontal scroll at 320px.** After the total raised changed to RM68,505, the automated overflow check failed at 320px (10px in Chromium, 11px in Firefox). A script listing every element wider than the viewport traced it to the total-raised sticker, whose number was too wide for the column. I made its font size scale with the viewport (`clamp(2rem, 10vw, 3.75rem)`) and the check passed again at every width.
- **Resolved: `form.name` bug.** In the first version, the "Choose format" button called `form.name.focus()`. `HTMLFormElement.name` is the form's own `name` attribute (a string), not the input called "name", so it would have thrown an error. I switched all field access to `form.elements.name` etc. and confirmed it with the automated interaction run below (focus lands on `#name`, no page errors).
- **Verification:** an automated browser script loads the page at each test width in Chromium and Firefox. It fails on horizontal overflow, console errors, failed requests or 4xx/5xx responses, then drives every interaction. After deploying, check the live URL in a private window, check that DevTools Network shows only HTTPS requests (no mixed content), and check that the favicon, fonts and hero image all load.

## Maintenance

- **Update content:** all text is in `index.html`, in sections with clear `id`s (`#how`, `#formats`, `#dates`, `#charity`, `#register`, `#faq`). For example, to change a date, edit both the visible text and the `datetime` attribute in `#dates`. To add a FAQ, copy a `<details>` block. To add a format, add a tab button, a panel and an `<option>` with the same value as the panel's `data-choose`.
- **Change brand colours or fonts:** edit the `@theme` tokens in `css/input.css`, run `npm run build`, then re-check contrast.
- **Redeploy:** `npm run build`, commit (including `css/styles.css`) and push to `main`. Pages redeploys automatically.
- **Restore a previous version:** `git revert <bad-commit>` then push. This keeps the history, and Pages redeploys the reverted state. To inspect an old version locally: `git checkout <hash>`.

## Security and third parties

- HTTPS only (GitHub Pages enforces it). All asset URLs are relative or `https://`.
- No credentials, API keys or environment variables anywhere in the project.
- **Third parties:** Google Fonts (CSS and font files) is the only external request. No analytics, trackers or third-party scripts. No runtime dependencies. The only dependencies are the Tailwind CLI and `tailwindcss` (dev only, pinned to 4.3.3). `npm audit` reports a high-severity denial-of-service advisory in `braces`, which the CLI's file watcher depends on. It only affects the build tool when it processes untrusted glob patterns, which doesn't happen here, and nothing from it is shipped to the browser. Playwright and axe-core were used only temporarily for testing and are not in this repo.

## Known limitations and what I'd do before production

- **The form is a demo.** In production it would need a real backend (or a form service) with server-side validation, spam protection, a privacy notice and consent wording, and real confirmation emails.
- **Google Fonts is a third-party request** that shares visitor IPs with Google. Before production I'd self-host the font files (WOFF2) and add a strict Content-Security-Policy.
- **No social sharing image** (`og:image`) or structured event data yet.
- **Dates are hard-coded** in the HTML, so registration doesn't close automatically after the deadline.
- Automated testing covered Chromium and Firefox engines. Safari/WebKit was only covered if it's noted under Testing above.
